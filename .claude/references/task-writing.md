## 팀 README

각 팀 `README.md`에는 다음 내용을 둔다.

- 회사, 팀, 기간과 기술 스택
- 팀에서 의미 있는 카테고리로 구분한 문서 목록 표
- 선택 항목인 기술 키워드 태그

문서 목록 표의 각 행에는 기간, 업무 한 줄 요약과 문서 링크를 넣는다.
링크 텍스트는 파일명이 아니라 대상 문서의 H1 제목을 사용한다.

## 업무 문서

- 진행 기간을 `**진행 기간**: 2024.06–2024.12` 형식으로 적는다.
- 회사명, 팀명과 내부 시스템 이름은 일반 표현으로 바꾼다. 팀 README의 회사와 팀 메타 정보는 그대로 둘 수 있다.
- 내부 URL과 IP는 제거하거나 `<내부-엔드포인트>`로 바꾼다.
- 운영 중인 상품과 서비스 이름은 공개하지 않고 동작과 구조를 설명하는 일반 표현으로 바꾼다.
- 새 문서를 추가하면 같은 팀 `README.md`의 문서 목록도 갱신한다.

## 업무 서사와 기술 개념

`task/`에는 업무의 배경, 막힌 지점, 내 기여, 협업과 회고를 작성한다.
기술 폴더에는 개념, 작동 원리와 일반적인 트러블슈팅을 작성한다.

업무 글에 긴 개념 설명이 필요하면 기술 폴더에 별도 문서를 만들고 연결한다.
한 업무가 기술 폴더에서 여러 문서로 정리돼 있다면 `task/` 글은 총괄과 목차 역할만 한다.

## 독자가 서비스와 설계 판단을 이해하는 글

업무 글은 독자가 서비스의 목적과 전체 구조를 이해한 뒤, 그 안에서 겪은 어려움과 해결 과정에서 배울 점을 얻도록 쓴다.
구현 항목이나 확인한 코드 목록보다 문제와 판단의 흐름을 중심에 둔다.

기본 흐름은 다음과 같다. 짧은 글에서는 절을 합치되, 독자가 필요한 맥락을 추측하게 두지 않는다.

1. **어떤 서비스인가**: 누가 어떤 문제를 해결하려고 쓰는지, 무엇을 입력받아 어떤 결과를 제공하는지 설명한다.
2. **전체 아키텍처와 내 역할**: 주요 데이터 흐름과 구성 요소의 책임을 먼저 보여 주고, 내가 맡은 부분을 짚는다. 구조가 이해에 도움이 되면 그림을 쓴다.
3. **어려웠던 점**: 어떤 조건이나 제약 때문에 기존 방식이 부족했는지 설명한다. 실제 사례와 확인한 현상으로 근거를 든다.
4. **해결과 진행 방향**: 선택한 방법과 이유, 검토한 대안과 비용을 연결한다. 구현한 것, 설계 중인 것과 다음 검증을 구분한다.
5. **검증과 배운 판단**: 확인한 결과와 남은 한계를 적고, 독자가 비슷한 문제에서 적용할 선택 기준을 남긴다. 일반 기술 설명이 길어지면 기술 문서로 연결한다.

## 근거와 공개 범위

사용자의 설명으로 목표와 관심사를 확인하고, 필요하면 관련 Dooray 업무·설계 기록과 GitHub 저장소의 문서·구현을 대조한다.
업무의 계획이나 완료 표시만으로 현재 구현·배포 상태와 효과를 단정하지 않는다.
현행 코드와 다른 과거 설계는 그 차이를 확인한 뒤 사용한다.

공개 글에는 독자가 이해할 수 있는 문제·판단·해결과 검증 한계를 남긴다.
사내 커밋 SHA, 비공개 저장소 주소, 내부 업무 번호와 링크, 회사 전용 코드 식별자와 검토 경위 목록은 공개 근거로 나열하지 않는다.
기여 검증에 필요한 비공개 상세는 저장소 밖의 검토 기록에 두고, 본인·동료·오픈소스·AI 도구의 역할은 업무 수준으로 구분한다.
실제 고객 기록, 비공개 정책과 수치를 공개 예시로 옮기지 않는다.
