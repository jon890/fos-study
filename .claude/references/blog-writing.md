# 공개 블로그 문서 작성

공개 학습 문서를 작성하거나 기존 글을 고칠 때 읽는다.

## 문서의 역할

기술 폴더에는 특정 업무와 분리해 언제 읽어도 유효한 개념을 작성한다.
실제 업무에서 얻은 경험은 `task/`에 두고 개념 문서와 상대 링크로 연결한다.

## 학습 문서의 깊이

짧은 요약보다 나중에 다시 공부할 수 있는 충분한 설명을 우선한다.
분량을 줄이기 위해 필요한 설명을 삭제하지 않고,
같은 결론을 반복하는 문장과 역할이 겹치는 예제만 정리한다.

- 기본 개념, 작동 원리, 선택 기준, 트레이드오프, 실패 사례와 검증 방법을 가능한 범위에서 함께 다룬다.
- 글만으로 관계를 파악하기 어려운 부분은 시각화한다.
- 장식만을 위한 시각화는 만들지 않는다.
- 버전에 따라 바뀌는 동작은 공식 문서에서 확인하고 적용 버전을 밝힌다.
- 잘못된 설명은 기존 표현을 보존하지 않고 근거에 맞게 수정한다.

## 시각화 형식

화면 크기와 글꼴이 달라져도 의미가 유지되는 형식을 선택한다.

- 흐름, 계층, 상태 변화와 구성요소 관계는 Mermaid를 우선한다.
- 서비스 흐름도, 시스템 구성과 상태 전이는 Mermaid로 표현한다.
- 공백과 고정폭 글꼴의 정렬이 의미를 결정하는 ASCII 도식은 블로그 본문에 사용하지 않는다.
- 같은 속성의 정확한 값이나 위치를 비교할 때는 Markdown 표를 사용한다.
- Mermaid와 표로 표현하기 어려운 공간 구조나 삽화가 필요할 때만 이미지 파일을 사용한다.
- 단순한 명령 출력과 정렬이 없어도 의미가 유지되는 짧은 예시는 `text` 코드 블록으로 남길 수 있다.
- Mermaid는 HTML 미리보기에서 노드 잘림, 연결 방향과 작은 화면의 가독성을 확인한다.

## 영어 기술 용어

직관적이지 않은 영어 운영·관측성 용어는 문서에서 처음 나올 때 `**영어**(한국어)` 형식으로 병기한다.
이후에는 영어만 사용한다.

- `Saturation`(포화도), `Latency`(지연), `Throughput`(처리량), `Backpressure`(배압) 같은 용어가 대상이다.
- `RPS`, `p99`, `traceId`, `circuit breaker` 같은 식별자와 관용 용어는 병기하지 않아도 된다.
- 검색과 실무에서 사용하는 영어 표기를 한국어로 완전히 대체하지 않는다.

## 관련 문서 링크

관련 상세 문서가 있으면 파일의 존재 여부를 확인하고 상대 경로로 연결한다.

- Markdown 문서 링크의 텍스트는 파일명이 아니라 대상 문서의 H1 제목을 사용한다.
- 전체 제목이 지나치게 길면 의미를 유지하는 범위에서 줄인다.
- 파일을 이동하거나 제목을 바꾸면 링크 경로와 링크 텍스트를 함께 갱신한다.

## 빠르게 읽을 수 있는 구조

- 링크 제목은 짧게 쓰고 설명은 다음 문단이나 목록으로 분리한다.
- 사례가 늘어날 수 있는 절은 H3 또는 표 구조로 시작한다.
- 본문 설명과 다른 문서를 가리키는 메모는 별도 문단으로 분리한다.
- 한 문단에 여러 정보가 묶이면 제목, 목록과 표 중 가장 작은 구조로 나눈다.

## 작성 후 검사

문서를 고친 뒤 다음 검사를 실행한다.

```bash
python3 ~/.claude/scripts/korean-style-check.py <파일.md>
python3 ~/.claude/scripts/check-readability.py <파일.md>
```
