# 블로그 작성 기준

## 업무 기록

업무 기록은 성과 목록보다 문제를 발견하고 판단한 흐름이 보이게 쓴다.

- 무엇이 문제였고 사용자나 운영에 어떤 영향을 줬는지 먼저 설명한다.
- 처음 가정과 실제 원인이 달랐다면 그 차이를 남긴다.
- 본인이 제안한 것, 구현한 것과 다른 사람에게서 확인한 것을 구분한다.
- 협업은 참석 사실보다 인터페이스나 설계가 어떻게 바뀌었는지로 설명한다.
- 결과는 측정한 값이나 재현 조건이 있을 때만 수치로 쓴다.

개인 글이므로 필요할 때 1인칭 단수를 쓸 수 있다. 모든 문장에 “나”를 반복하거나 이력서 문장처럼 성과를 나열하지 않는다.

권장 흐름은 다음과 같다. 글의 성격에 맞지 않는 항목은 생략한다.

1. 배경과 문제
2. 예상과 달랐던 지점
3. 원인 확인 과정
4. 선택한 해결과 트레이드오프
5. 검증 결과
6. 다음에 바꿀 판단

## 학습 문서

학습 문서는 용어 목록보다 다시 적용할 수 있는 이해를 남긴다.

- 작동 원리와 데이터 흐름을 설명한다.
- 선택지가 여러 개라면 선택 기준과 비용을 비교한다.
- 실패 조건과 검증 방법을 함께 둔다.
- 직접 사용하지 않은 기술은 사용 경험처럼 쓰지 않는다.
- 일반 기술에 임의의 채용 포지션이나 가상 도메인을 붙이지 않는다.

## 코드와 수치

코드의 클래스명과 API는 실제 코드 또는 공식 문서에서 확인한다. 축약했으면 의사코드임을 밝힌다.

수치는 출처나 측정 조건과 함께 쓴다. 측정하지 않은 개선율, 임의의 SLA와 빈 자리표시자는 만들지 않는다. 계산이 글의 판단을 바꾸지 않으면 장식용 수치를 넣지 않는다.

## 구조

제목, 첫 단락과 결론이 같은 질문에 답하게 한다. 다음 패턴은 초안에서 제거한다.

- 같은 결론을 본문, 표와 체크리스트로 반복함
- 어느 글에도 붙일 수 있는 중요성 설명
- 근거 없이 대칭을 맞춘 장단점 목록
- 내용을 소개하기만 하는 긴 목차 해설
- 독자 이해를 돕지 않는 Mermaid나 장식 이미지

흐름, 계층, 상태 변화와 구성요소 관계는 글보다 시각화가 명확할 때만 Mermaid·ASCII 도식이나 표로 표현한다.
