# fos-study 블로그 글 작성

저장소의 `CLAUDE.md`를 먼저 읽고 폴더 배치, 역할 태그, 민감 정보와 문서 깊이 규칙을 따른다. 이 스킬에는 저장소 규칙을 복제하지 않는다.

## 문서 역할 결정

글을 쓰기 전에 저장소 전체에서 같은 주제를 검색하고 다음 중 하나를 선택한다.

| 판정 | 동작 |
| --- | --- |
| 새 주제 | 새 파일을 만든다. |
| 기존 글의 빈 부분 | 기존 글을 보강한다. |
| 기존 글이 이미 충분함 | 새 파일을 만들지 않고 기존 글을 안내한다. |
| 업무 서사와 기술 개념이 섞임 | `task/`에는 경험을, 기술 폴더에는 일반 개념을 두고 서로 연결한다. |
| 두 글의 역할을 가르기 어려움 | 사용자에게 방향을 묻는다. |

역할 태그는 `tasks` 또는 `study`를 기본으로 사용한다. 실제 경험에서 얻은 재사용 가능한 판단이 본문에 분명할 때만 `insights`를 추가한다.

## 업무 기록

업무 기록을 작성할 때는 다음 근거를 먼저 확인한다.

- 본인 커밋, PR과 실제 코드에서 기여 범위와 진행 기간을 확인한다.
- 기억으로 클래스명, 메서드명과 측정값을 만들지 않는다.
- 코드와 내부 식별자는 [공개 범위](./references/publishing-policy.md)를 적용한다.
- 일반 기술 설명이 길어지면 기술 폴더 문서로 분리하고 링크한다.

업무 서사의 표현과 구성은 [작성 기준](./references/writing-style.md)을 읽고 적용한다.

## 학습 문서

학습 문서는 현재 동작이 바뀔 수 있는 주장을 공식 문서, 논문이나 원저장소에서 확인한다. 적용 버전을 밝히고 출처의 사실, 직접 확인한 결과와 추론을 구분한다.

특정 회사·포지션·면접을 위한 가상 도메인을 일반 기술 주제에 붙이지 않는다. 이미 섞인 글을 고칠 때는 일반 개념만 기술 문서에 남기고 실제 업무 경험은 해당 `task/` 문서로 옮기거나 연결한다.

## 작성과 검증

1. 초안을 쓴 뒤 제목과 첫 단락이 같은 질문에 답하는지 확인한다.
2. 중복 결론, 장식용 표와 근거 없는 수치를 제거한다.
3. 내부 링크는 대상 파일이 존재하는지 확인한다.
4. [fos-blog 마크다운](./references/markdown-pitfalls.md)의 실제 렌더링 제약을 적용한다.
5. 새 글에 대표 이미지가 필요하면 [썸네일 생성](./references/thumbnail-generation.md)을 따른다.
6. 프로젝트의 한국어 표현 검사와 가독성 검사를 실행한다.
7. 파일을 이동·삭제했거나 링크를 바꿨으면 `docs-audit` 구조 검사도 실행한다.

## 미리보기와 발행

로컬 파일 작성은 곧바로 진행할 수 있다. 블로그 반영을 위한 commit과 push까지 요청받았다면 다음 순서를 지킨다.

1. `scripts/render_preview.mjs <글.md> <preview.html>`로 저장소 밖 `/private/tmp/`에 HTML을 만든다.
2. `content-preview` 스킬로 변경된 게시 글과 렌더링 결과를 사용자에게 보여준다.
3. 미리보기를 보여준 턴에는 push하지 않는다.
4. 사용자가 확인한 다음 관심사별 원자적 커밋을 만들고 push한다.

삭제만 한 변경에는 본문 미리보기가 필요하지 않다. 새로 작성하거나 의미 있게 고친 공개 글은 미리보기 대상이다.
