# Confluence 문서를 OpenSearch에 벡터 색인하기: Spring Batch 파이프라인 설계기

**진행 기간**: 2026.01–2026.03

사내 문서를 검색해 답변의 근거로 사용하는 서비스에 Confluence 색인 배치를 설계하고 구현했다.
페이지를 읽어 임베딩하는 기본 흐름에서 시작해 댓글과 첨부파일, 변경 감지, 삭제 반영과 여러 스페이스 지원까지 확장했다.

이 글은 Spring Batch 사용법보다 구현 중 결정한 데이터 경계와 실패 처리에 초점을 둔다.

## 색인 범위

배치가 처리해야 할 데이터와 동기화 조건은 다음과 같았다.

| 구분 | 처리 내용 |
| --- | --- |
| 원본 | Confluence 페이지, 댓글과 첨부파일 |
| 변환 | ADF 본문을 Markdown으로 변환하고 첨부파일은 Document Parser로 파싱 |
| 검색 데이터 | 본문 임베딩과 제목, 작성자 및 문서 위치 메타데이터 |
| 증분 처리 | 원본 버전과 색인 버전을 비교해 변경된 문서만 다시 처리 |
| 삭제 반영 | 삭제되거나 휴지통으로 이동한 페이지와 댓글을 색인에서도 제거 |
| 실행 단위 | 스페이스마다 다른 연결 정보와 색인 설정을 잡 파라미터로 전달 |

전체 흐름은 다음과 같다.

```mermaid
flowchart LR
    A[스페이스 정보 조회] --> B[페이지와 댓글 수집]
    B --> C{버전 변경 여부}
    C -->|변경 없음| D[건너뜀]
    C -->|변경됨| E[본문과 메타데이터 보강]
    E --> F[ADF를 Markdown으로 변환]
    F --> G[임베딩 API 호출]
    G --> H[OpenSearch 색인]
    H --> I[삭제 상태 동기화]
```

## Spring Batch 선택

외부 API 세 곳을 호출하는 작업이라 일부 요청의 지연과 실패를 피할 수 없었다.
처리 대상을 청크로 나누고 페이지 색인, 댓글 색인과 삭제 반영을 별도 Step으로 분리했다.

Spring Batch의 실행 이력은 어느 Step에서 실패했는지 확인하는 데 사용했다.
청크 경계는 한 번에 메모리에 올리는 데이터와 OpenSearch에 쓰는 단위를 제한했다.
이 선택으로 모든 로직이 자동으로 재시작 가능한 것은 아니었고, Step 사이에서 공유하는 데이터의 저장 위치를 따로 결정해야 했다.

## Step 사이 데이터의 저장 위치

스페이스 정보와 페이지 ID 목록은 뒤 Step에서 댓글과 첨부파일을 조회할 때 필요했다.
처음에는 `JobExecutionContext`에 넣었지만, 페이지 ID처럼 큰 작업 데이터를 배치 메타데이터로 직렬화하는 것은 역할이 맞지 않았다.

이 데이터는 `@JobScope`인 잡 범위 홀더에 두었다.
잡 실행 동안만 메모리에 유지되므로 도메인 작업 데이터와 재시작 상태를 분리할 수 있었다.

대신 잡을 재시작하면 홀더가 새로 만들어진다.
홀더를 채우는 Step에는 `allowStartIfComplete(true)`를 적용해 이전 실행에서 완료됐더라도 다시 실행하도록 했다.
작업 데이터를 메모리에 둔 선택에는 초기 조회를 다시 해야 한다는 비용이 있었다.

## 색인 처리 단계

페이지와 댓글은 같은 처리 순서를 사용했다.

1. OpenSearch의 기존 버전과 원본 버전을 비교한다.
2. 변경된 문서에 첨부파일, 작성자와 멘션 정보를 보강한다.
3. ADF 본문을 Markdown으로 변환한다.
4. 본문과 첨부파일에서 임베딩을 만든다.
5. 임베딩과 메타데이터를 OpenSearch에 쓴다.

각 단계는 별도 `ItemProcessor`로 나누고 `CompositeItemProcessor`로 연결했다.
변경 감지에서 `null`을 반환하면 이후의 문서 파싱과 임베딩 호출을 건너뛴다.
비용이 드는 외부 호출 앞에서 변경 여부를 먼저 확인하도록 순서를 정했다.

### 임베딩 호출의 제한된 병렬 처리

임베딩은 CPU 계산보다 외부 응답을 기다리는 시간이 긴 작업이었다.
동기 처리에서는 한 문서의 응답을 받은 뒤 다음 문서를 요청해 대기 시간이 누적됐다.

`AsyncItemProcessor`와 `AsyncItemWriter`를 사용해 여러 문서의 임베딩 요청을 제한된 스레드 풀에서 처리했다.
Writer는 `Future` 결과를 확인한 뒤 기존 OpenSearch Writer에 전달했다.

이 구조는 병렬 요청 수를 executor 설정으로 제한한다.
임베딩 API의 수용량보다 요청을 많이 보내지 않도록 스레드 수와 대기열을 운영 설정에서 조절할 수 있게 했다.

일반 동작은 [AsyncItemProcessor](../../java/spring-batch/async-item-processor.md)에 따로 정리했다.

## Confluence 본문의 검색 가능한 형태 변환

Confluence Cloud의 ADF 본문은 JSON 트리다.
JSON을 그대로 임베딩하지 않고 제목, 목록, 표, 코드 블록과 링크의 구조를 Markdown으로 변환했다.

변환기는 ADF 노드 유형별 처리만 담당하고, 색인 Processor는 변환기 인터페이스에 의존하도록 나눴다.
지원하지 않는 노드를 추가할 때 임베딩과 OpenSearch 처리까지 함께 고치지 않기 위한 경계였다.

첨부파일은 배치가 직접 해석하지 않고 Document Parser에 전달했다.
큰 파일을 바이트 배열 전체로 보관하지 않도록 다운로드 응답을 스트림으로 넘겼다.
ZIP 파일은 내부 파일별로 파싱해 서로 다른 문서의 내용이 하나의 검색 항목에 합쳐지지 않도록 했다.

## 변경 감지와 삭제 반영

전체 문서를 실행할 때마다 다시 임베딩하면 외부 API 비용과 처리 시간이 반복된다.
원본 문서 버전과 OpenSearch의 `version` 메타데이터를 비교하고, 값이 같은 문서는 뒤 처리 단계로 보내지 않았다.

삭제는 변경 감지와 다른 방향의 동기화다.
Confluence API에서 `DELETED`와 `TRASHED` 상태를 조회해 해당 페이지와 댓글을 OpenSearch에서도 제거했다.
색인과 삭제를 별도 Step으로 분리해 어느 단계에서 실패했는지 실행 이력으로 구분했다.

외부 의존성 오류가 반복된 문서는 실패 횟수를 기록했다.
정해진 횟수를 넘긴 문서를 계속 재요청하지 않아 한 문서가 전체 배치 시간을 반복해서 소비하지 않도록 했다.
자체 코드 오류까지 같은 방식으로 제외하면 수정 후에도 문서가 계속 빠질 수 있으므로, 외부 호출 실패만 이 기록의 대상으로 삼았다.

## 여러 스페이스의 연결 정보

스페이스마다 Confluence 주소와 인증 정보가 달랐다.
클라이언트를 하나의 고정 빈으로 만들면 실행마다 다른 연결 정보를 사용할 수 없었다.

잡 파라미터로 연결 정보와 스페이스 키를 받고, factory가 실행에 맞는 API 클라이언트를 만들도록 바꿨다.
Reader와 Processor는 구체적인 HTTP 클라이언트 대신 서비스 인터페이스를 사용했다.

색인 메타데이터도 대상에 따라 필요한 필드가 달랐다.
조건문을 임베딩 Processor에 넣지 않고 별도 Provider 인터페이스로 메타데이터 생성을 분리했다.
필드 구성이 바뀌어도 본문 변환과 임베딩 순서를 건드리지 않도록 했다.

## 빈 이름 충돌

여러 배치 잡이 같은 타입의 `@StepScope` 빈을 각각 등록하면서 `NoUniqueBeanDefinitionException`이 발생했다.
타입만으로는 어느 Processor를 주입할지 정할 수 없었다.

잡마다 동작이 다른 빈은 설정 클래스에서 이름을 분리하고 `@Qualifier`로 선택했다.
여러 잡이 완전히 같은 방식으로 사용하는 Reader와 Writer는 공용 `@Component`로 한 번만 등록했다.

이 문제는 처리 로직의 오류가 아니라 Spring 컨텍스트 구성 오류였다.
Processor 단위 테스트만으로는 찾기 어려워 실제 빈을 올리는 컴포넌트 테스트가 필요했다.

## 검증

외부 서비스는 고정 응답으로 대체하고 Spring 빈은 실제로 구성하는 컴포넌트 테스트 애노테이션을 만들었다.
다음 경계를 나누어 검증했다.

- ADF 입력이 예상한 Markdown 구조로 변환되는지 확인했다.
- Reader가 커서 기반 다음 페이지를 이어서 조회하는지 확인했다.
- 문서 버전이 같을 때 변경 감지 Processor가 뒤 단계를 건너뛰는지 확인했다.
- 작성자, 멘션과 첨부파일 정보가 색인 입력에 포함되는지 확인했다.
- 메타데이터 Provider와 OpenSearch Writer가 약속한 필드를 만드는지 확인했다.
- 설정한 빈 이름과 `@Qualifier`로 애플리케이션 컨텍스트가 올라오는지 확인했다.

외부 HTTP 호출만 모킹하고 실제 Processor와 Writer를 연결했기 때문에, 순수 단위 테스트에서 놓치기 쉬운 빈 충돌과 처리 순서도 함께 확인할 수 있었다.

## 내가 한 일

- Confluence 수집부터 Markdown 변환, 임베딩과 OpenSearch 색인까지 배치 흐름을 설계하고 구현했다.
- 페이지와 댓글, 첨부파일 처리 및 삭제 상태 동기화를 별도 Step으로 구성했다.
- 버전 비교를 앞단에 두어 변경된 문서만 파싱하고 임베딩하도록 했다.
- 임베딩 호출을 제한된 병렬 처리로 바꾸고 실행 설정에서 동시 요청 수를 조절하도록 했다.
- 여러 스페이스의 연결 정보와 메타데이터 차이를 factory와 Provider 경계로 분리했다.
- ADF 변환기와 배치 컴포넌트 테스트를 추가했다.

## 배운 것

배치 메타데이터와 작업 데이터는 크기뿐 아니라 재시작 때 필요한지로 나눠야 했다.
메모리 홀더를 선택하면 직렬화를 피할 수 있지만, 재시작 때 데이터를 다시 채우는 Step이 필요하다.

비동기 처리는 외부 API 대기 시간을 겹칠 수 있지만 동시 요청 수를 함께 제한해야 한다.
병렬화 자체보다 임베딩 API가 감당할 요청 수와 실패 시 처리 방식이 먼저였다.

증분 색인은 새 문서를 쓰는 작업만으로 끝나지 않는다.
변경되지 않은 문서를 건너뛰는 기준과 원본에서 사라진 문서를 제거하는 기준을 함께 구현해야 검색 결과가 원본과 맞았다.
