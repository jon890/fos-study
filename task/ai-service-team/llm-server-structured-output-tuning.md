# LLM 응답이 공백과 빈 항목을 반복했을 때 바꾼 설정

**진행 기간** 2026.11

정해진 JSON을 받아 후속 처리를 하는 작업에서 모델이 필드 사이에 공백을 반복했다. 호출별 출력 상한을 걸자 비용은 제한됐지만 JSON이 닫히기 전에 잘릴 수 있었다. 이후에는 배열에서 빈 객체가 반복된 경우와 JSON 앞에 설명이나 도구 표식이 붙어 읽을 수 없었던 경우도 확인했다. 설정마다의 개념은 [vLLM 서버 옵션 지도](../../mlops/llm-serving/vllm-serving-options.md)에 따로 정리했다.

## 공백 반복과 서버 부하에 대응한 설정

표의 설정 칸에는 서버 설정 값과 함께 그 설정이 하는 일을 한 줄로 적었다. 개념이 처음이면 링크한 절부터 읽는다.

| 설정 | 선택 이유 |
| --- | --- |
| `backend: xgrammar`, `disable_any_whitespace: true`. 모델이 다음 토큰을 고를 때 JSON 스키마에 맞는 토큰만 남기는 라이브러리(XGrammar)를 쓰고, 괄호와 쉼표 주변의 선택적 공백을 허용하지 않는다. [구조화 출력](../../mlops/llm-serving/vllm-serving-options.md#구조화-출력) | 필드 사이의 공백 반복으로 출력 예산을 쓰는 경로를 닫았다. 공유 서버 설정이어서 같은 백엔드의 구조화 출력 경로도 함께 확인했다 |
| 배열마다 `maxItems: 60`, 필요한 근거 배열에 `minItems: 1`, 필수 필드와 값 제약. 스키마에 적은 개수와 필수 칸을 어기는 토큰도 생성 중에 막힌다. [구조화 출력](../../mlops/llm-serving/vllm-serving-options.md#구조화-출력)의 「스키마 제약이 반복을 막는 이유」 | 정상 응답 기록에서 변경 배열의 최대 길이는 28이었다. 이 길이에 여유를 두고 배열 상한을 정했다. 정상적으로 변경이 없는 응답은 빈 배열을 허용하고, 변경이 있다면 필수 필드와 비어 있지 않은 근거를 요구했다 |
| `--max-num-seqs 32`. GPU에서 함께 계산하는 요청 수의 상한이다. 넘친 요청은 실패하지 않고 서버 안에서 기다린다. [스케줄링과 동시 처리](../../mlops/llm-serving/vllm-serving-options.md#스케줄링과-동시-처리) | 처음 24로 두었을 때 정기 작업 시간에 대기 요청이 최대 18건 쌓였다. 동시 32 부하에서 32가 24보다 출력 처리량이 약 17% 높고 첫 토큰 p50이 약 5초에서 0.45초로 줄어 32로 올렸다 |
| `--tensor-parallel-size 8`, `--enable-expert-parallel`. 모델 가중치를 GPU 8장에 나눠 올리고, MoE 층은 expert 단위로 나눈다. [모델을 여러 GPU에 나눠 올리기](../../mlops/llm-serving/vllm-serving-options.md#모델을-여러-gpu에-나눠-올리기) | 큰 MoE 모델을 GPU 8장에 배치하던 기존 구성을 유지했다 |
| DSpark 초안 4개, 확률적 초안 샘플링과 블록 검증, 적응형 검증 끔. 작은 초안 모델이 토큰 4개를 먼저 쓰고 큰 모델이 한 번에 검증하는 추측 디코딩 설정이다. [빠르게 생성하기](../../mlops/llm-serving/vllm-serving-options.md#빠르게-생성하기) | 초안 수는 기존 부하 비교에서 고른 값을 유지했다. 적응형 검증 경로에서 종료가 관찰돼 해당 기능을 껐다. 이 관찰로 종료의 근본 원인까지 확정할 수는 없다 |
| GPU 메모리 비율과 최대 문맥 길이 미지정. 각각 KV cache에 줄 메모리 크기와 요청 하나의 최대 길이를 정하는 옵션이다. [메모리와 문맥 길이](../../mlops/llm-serving/vllm-serving-options.md#메모리와-문맥-길이) | 고정 이미지에서 쓰던 기본 동작을 유지했다. Compose에 수치가 없어 공개 릴리스의 기본값으로 대신 계산하지 않았다 |
| 모델에 맞는 추론·도구 파서와 자동 도구 선택 유지. 모델 출력에서 생각 구간과 도구 호출을 찾아 응답의 칸별로 나누는 설정이다. [출력 다루기](../../mlops/llm-serving/vllm-serving-options.md#출력-다루기) | 기존 호출의 응답 구분과 도구 선택 방식을 유지했다. JSON만 필요한 요청은 도구 선택을 끄고 스키마를 전달하는 경로를 점검했다 |
| 모델 호출당 출력 상한 8,192토큰. 서버 옵션이 아니라 요청마다 보내는 값이다. [출력 상한과 해석 실패를 확인하는 법](../../mlops/llm-serving/vllm-serving-options.md#출력-상한과-해석-실패를-확인하는-법) | 공백 반복이나 긴 생성이 요청 예산을 넘지 않도록 했다. 상한에 걸린 응답은 잘린 원문과 종료 사유를 함께 확인했다 |

[사내 LLM 서버의 추측 토큰 수를 7에서 4로 줄인 기록](./llm-server-speculative-tokens-tuning.md)

## 확인한 범위

공백 제한을 적용한 뒤 비교를 세 번 돌렸다. 114회 중 추적 기록이 남은 모델 응답 111건은 JSON 문자열 밖 공백 없이 끝났고 출력 상한에도 닿지 않았다. 나머지 세 실행은 모델 응답이 남기 전에 실패했다.

운영 이미지의 XGrammar 0.2.8에서 보강한 스키마를 컴파일했고 검사 사례 10개가 모두 통과했다. 정상 빈 응답과 정상 변경, 배열 상한까지는 허용했다. 빈 객체 반복, 필수 값이 빈 문자열이거나 `null`인 응답, 빈 근거와 배열 상한 초과는 거부했다. 설명이 붙는 문제는 호출 경로에서 별도로 확인했다. 도구 선택을 끄고 스키마를 보낸 개발 환경 점검에서 설명 없이 JSON이 끝난 사례를 확인했다. 이 점검은 동일 오류의 재발률과 동시 처리량을 측정한 부하 테스트와 범위가 다르다.
