# RAG 시스템 설계는 사용 흐름, 추론 경로, 입력 품질 세 축으로 나눠 진단한다

RAG 를 개선한다고 하면 임베딩 모델이나 벡터 DB 부터 바꾸고 싶어진다.
하지만 같은 RAG 를 만든 회사들의 사례를 나란히 놓고 보면, 성패는 검색 기법 하나보다 사용자가 일하는 흐름, 질문별 추론 경로, 입력 문서의 품질에서 갈린다.
이 글은 토스, 우아한형제들, Sionic AI 의 RAG 사례를 비교한 분석 자료를 바탕으로, RAG 시스템을 세 축으로 진단하는 방법과 어떤 순서로 측정할지 정리한다.

바탕이 된 자료는 세 회사의 사례를 NotebookLM 으로 요약한 슬라이드다.
슬라이드에는 원문 링크가 없어 회사별 세부 내용과 수치는 원 출처로 확인하지 않았다.
그래서 이 글은 사례의 세부 수치보다 사례들을 비교해서 얻는 진단 틀에 무게를 둔다.

## 세 축

| 축 | 핵심 질문 | 사례에서 얻은 교훈 |
| --- | --- | --- |
| Workflow | 검색 결과가 사용자가 이미 일하는 곳에 도착하는가 | 별도 검색 화면보다 메신저와 IDE 같은 기존 흐름에 통합한다 |
| Logic | 질문 의도에 따라 검색과 추론 경로가 달라지는가 | 하나의 거대한 프롬프트보다 분류와 특화 경로로 책임을 나눈다 |
| Data Quality | 원문이 검색과 생성에 적합한 구조로 보존되는가 | 모델을 바꾸기 전에 파싱, 표 구조, 읽기 순서를 검증한다 |

### Workflow: 토스의 사내 기술 문서 RAG

토스 프론트엔드 팀의 '박씨' 는 사내 라이브러리와 기술 문서에 답하는 RAG 시스템이다.
분석 자료는 핵심 전략을 검색 엔진을 만드는 것이 아니라 개발자가 가장 선호하는 "질문하기" 경험을 IDE 와 메신저에 통합하는 것으로 요약한다.
Slack 에서 질문하면 답이 오는 방식이고, 문서가 낡는 문제는 코드 주석에서 문서를 만들고 주석이 없으면 CI 를 실패시키는 방식으로 다룬다.
이 사례의 상세는 [토스 : 100번 실패하고 살려낸 문서 시스템](./toss-parkssi.md)에 있다.

### Logic: 우아한형제들의 Text-to-SQL

우아한형제들의 '물어보새' 는 SQL 을 못 쓰는 구성원이 자연어로 데이터를 뽑게 하는 시스템이다.
분석 자료가 정리한 설계는 다음과 같다.

- 질문을 받으면 라우터가 의도를 분류하고, 의도별로 특화된 체인으로 보낸다. SQL 생성, 해설, 문법 검증, 테이블 탐색 체인이 있다.
- 정확도를 높이는 과정을 데이터 보강, 검색 알고리즘, 프롬프트 엔지니어링, 평가 시스템 네 단계로 나눈다. 테이블 목적과 컬럼 설명 같은 메타데이터를 보강하고, 질문 의도에 맞는 테이블 정의와 검증된 SQL 예제를 동적으로 꺼내 쓴다.
- 쿼리를 실행하기 전에 문법을 검증해 오류를 미리 막는다.
- 사용자의 좋음과 나쁨 평가를 모아 좋은 답변은 캐시해서 재사용한다.

단일 프롬프트로 모든 질문을 처리하지 않고, 의도에 맞춰 경로를 나눈 것이 Logic 축의 사례다.

### Data Quality: Sionic AI 의 문서 파싱

Sionic AI 는 RAG 성능의 병목을 문서 파싱으로 본다.
문서 구조가 깨지면 LLM 은 정답을 찾을 수 없다는 주장이다.
분석 자료가 소개한 접근은 두 가지다.

- **두 단계 변환**: 기존 파서로 텍스트 구조를 먼저 뽑고, 원본 이미지를 VLM(Vision-Language Model)에 보여 줘 깨진 표, 병합 셀, 차트를 다시 해석한다.
- **자연어 직렬화**: 표의 한 행을 `과목: 통계학 | 학점: 3` 로 두지 않고 "통계학 과목은 3학점이며 1학기에 개설됩니다" 같은 문장으로 바꾼다. 자료는 임베딩 모델이 표 형식보다 자연어 문장을 더 잘 이해하고, 청킹으로 잘려도 문장 단위로 맥락이 남는다고 설명한다.

슬라이드의 정확도 비교 수치는 벤더가 제시한 값이라 이 글에서는 옮기지 않는다.
이 사례의 제품 소개는 [STORM Parse](./storm-parse.md)에 있다.

## 어떤 순서로 측정할 것인가

세 축은 서로 독립이 아니다.
이 글이 제안하는 진단 순서는 파이프라인의 앞쪽부터 보는 것이다.
앞 단계가 깨져 있으면 뒤 단계의 지표가 좋아도 의미가 없기 때문이다.

| 순서 | 측정할 것 | 먼저 확인하는 이유 |
| --- | --- | --- |
| 1 | 입력의 완전성과 신선도 | 수집 누락, 삭제 동기화 실패, 갱신 실패가 있으면 이후 모든 단계가 틀린 데이터 위에서 돈다 |
| 2 | 변환 품질 | 문서와 표의 구조가 chunk 로 나눈 뒤에도 보존되는지 본다 |
| 3 | 검색 품질 | Recall@K, MRR, nDCG 로 후보 집합과 순위를 본다 |
| 4 | 최종 답변 | 근거성, 정확성, 사용자의 작업 완료 여부를 본다 |

1번과 2번은 모델을 바꿔도 같은 증상이 반복된다.
생성 모델을 교체하기 전에 파서와 평가 데이터를 먼저 보는 것이 이 순서의 이유다.

## 설계 판단

- 사용 흐름이 나쁘면 검색 정확도가 높아도 채택되지 않는다.
- 추론 경로가 복잡해질수록 단계마다 실패 이유와 대체 경로가 보여야 한다.
- 입력 품질 결함은 생성 모델을 바꿔도 반복되므로 파서와 평가셋을 먼저 본다.
- 비결정적인 평가 앞에는 스키마, 누락, 구조 같은 결정적 검사를 둔다.
- 검색 품질은 단일 모델이 아니라 질문 구조화, 후보 검색, 필터, 재정렬의 조합으로 개선한다.
- GraphRAG 는 그래프 구축과 검색을 분리하고, 질문에 맞는 경로를 남기는 문제로 본다.
