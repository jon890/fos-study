# 스킬이나 프롬프트를 자동으로 고치려면 먼저 채점 신호를 설계해야 한다

스킬 문서나 프롬프트를 에이전트가 스스로 고치게 하는 자동 최적화 루프가 있다.
문서를 편집하고, 과제를 다시 돌려 채점하고, 점수가 오를 때만 그 편집을 채택하는 구조다.
이 루프에서 가장 어려운 부분은 편집을 만드는 쪽이 아니라 채점하는 쪽이다.
이 글은 자동 최적화를 붙이기 전에 채점 신호를 어떻게 분류하고, 어떻게 나누어 배치하고, 어떻게 믿을 수 있게 만들지 정리한다.
특정 도구의 사용법은 다루지 않고 어떤 도구에도 적용되는 원칙만 다룬다.

## 채점 신호가 없으면 편집이 채택되지 않는다

자동 최적화는 "이 편집이 나아졌는가" 를 점수로 판정한다.
점수를 낼 수 없으면 어떤 편집도 채택 기준을 통과하지 못한다.
머신러닝으로 말하면 손실 함수 없이 학습을 돌리는 것과 같다.
백엔드 개발로 말하면 테스트가 없는 코드를 자동으로 리팩터링하려는 것과 같다.

그래서 필요한 것은 두 가지다.

- **채점 함수(reward)**: 결과물에 점수를 매기는 함수
- **held-out 검증셋**: 편집을 만드는 데 쓰지 않은 과제 묶음. 편집이 훈련 과제에만 맞춘 것이 아닌지 확인한다

채점 신호의 정의가 자동화의 선행 조건이다.
신호가 정의되지 않은 스킬은 자동 최적화 대상이 아니다.

## 스킬을 채점 가능성으로 분류하기

스킬마다 채점 신호의 상태가 다르므로 먼저 세 계층으로 나눠 본다.

| 계층 | 채점 신호 | 예 | 자동화 |
| --- | --- | --- | --- |
| A | 통과와 실패 같은 객관 신호가 이미 있다 | 문서 검사기나 린터를 돌리는 스킬 | 바로 학습 루프를 돌릴 수 있다 |
| B | 규칙 체크리스트를 위반 수로 환산하면 점수가 된다 | 글쓰기 규칙을 지키는 스킬 | 규칙만으로는 핵심 품질을 못 잡아 LLM judge 를 섞는다 |
| C | 정답이 없다 | 브라우저 자동화, 외부 API 래퍼 | 본체 학습이 불가능하다 |

C 계층에 정답이 없는 이유는 부수효과, 승인 흐름, 외부 상태 변동 때문이다.
같은 입력으로 다시 돌려도 결과가 같지 않으면 점수의 변화가 편집의 효과인지 환경의 변화인지 구분할 수 없다.

미리보기를 보여 주고 사람이 확인한 뒤 진행하는 대화형 워크플로도 자동 채점 루프와 근본적으로 맞지 않는다.
사람의 판단이 루프 안에 들어 있기 때문이다.
이런 스킬에서는 도구를 쓰지 않고 규율만 빌린다.
빌릴 수 있는 규율은 한 번에 고치는 양을 제한하는 편집 예산과, 채택 전에 점검하는 검증 단계다.

## 채점을 두 계층으로 나눈다

B 계층의 스킬은 규칙으로 잡을 수 있는 부분과 판단이 필요한 부분이 섞여 있다.
이를 한 가지 방법으로 채점하지 않고 두 계층으로 나눈다.

| 계층 | 방식 | 맡는 일 |
| --- | --- | --- |
| 1계층 바닥 | 정적 검사(정규식, 사전) | 알려진 명백한 패턴이 돌아오지 않게 막는다 |
| 2계층 천장 | LLM judge | 정규식이 못 보는 의미 품질과 사전에 없는 새 표현을 본다 |

1계층은 비용이 없고 결과가 항상 같다.
반복되는 패턴을 확실히 막는다.

2계층은 인사이트가 있는가, 글에서 AI 티가 나는가, 서사 흐름이 이어지는가 같은 의미 품질을 본다.
1계층을 통과한 결과만 judge 에 올리면 호출 비용이 준다.

### 어느 계층에 둘지는 오탐 위험으로 정한다

검출 대상을 어느 계층에 둘지는 오탐(false positive) 위험이 기준이다.

- 정당한 용례가 거의 없는 명백한 항목만 정적 사전에 좁게 넣는다.
- 맥락에 따라 정당할 수 있는 항목은 judge 에 맡긴다.

정적 사전에 넣은 항목은 걸리면 곧바로 감점이므로, 정당한 용례가 있는 항목을 넣으면 멀쩡한 글이 감점된다.

### judge 의 함정을 막는 두 장치

LLM judge 는 같은 입력에도 점수가 흔들리고 후하게 매기는 경향이 있다.
이를 막는 장치는 두 가지가 있다.

- **N회 호출의 중앙값**: 같은 입력을 여러 번 채점해 중앙값을 쓰면 이상치가 사라진다.
- **약점 먼저 찾기**: 매 호출이 약점을 먼저 찾아 적은 뒤에 점수를 매기게 하면 점수 인플레이션이 줄어든다.

judge 의 편향과 사람 라벨을 이용한 검증은 [LLM 평가 프레임워크](../ops/llm-evaluation-framework.md)에서 다룬다.
이 글에서 보태는 것은 judge 앞에 정적 바닥을 두는 배치다.

이 두 장치는 설계 논의에서 나온 것이고 효과를 측정한 값은 없다.
적용할 때는 자신의 judge 로 점수의 흔들림을 직접 측정한다.

## 오탐을 먼저 제거한다

위반 수를 reward 로 쓰는 정적 검사는 오탐을 먼저 없애야 한다.
오탐이 있는 채로 최적화하면 가짜 위반을 줄이는 쪽으로 학습이 흐르기 때문이다.
이 경우 점수는 오르지만 멀쩡한 부분이 망가진다.

작성자의 작업 중에 같은 문제가 두 번 나왔다.
건수는 기록으로 확인되지 않아 적지 않는다.

- 굵은 글씨 안에 있는 마크다운 링크의 `(url)` 부분을 굵은 글씨 뒤의 괄호 위반으로 센 검사기
- 자기 경험이 출처인 문서까지 출처 누락으로 센 검사기

정적 검사를 reward 로 쓰기 전에 다음을 한다.

1. 검출된 위반을 무작위로 몇 개 뽑아 실제 위반인지 사람이 확인한다(spot-check).
2. 오탐이 나오면 검사기를 고쳐 "이것은 위반이 아니다" 를 코드에 남긴다.
3. 면제 기준은 코드에 명시한다. 예를 들어 자기 경험이 출처인 문서는 출처 항목을 면제하고, 의도적인 범위 표기는 이스케이프로만 처리한다.

3번에서 오탐 사유를 코드에 쌓는 것은 자동 최적화 도구가 거부된 편집을 기억해 두었다가 같은 편집을 다시 제안하지 않는 것과 같은 효과를 낸다.
같은 오탐을 다시 잡지 않게 만든다.

## 스킬 문서 자체를 채점하기

스킬 문서의 품질도 같은 구조로 채점할 수 있다.
다만 두 가지 축을 서로 다른 도구가 맡는다.

| 축 | 담당 | 재현성 | 예 |
| --- | --- | --- | --- |
| 기계축 | 스크립트 | 항상 같은 값 | 본문 줄 수, 끊긴 참조 수, 표기 위반 수 |
| 판단축 | 독립 검토 에이전트 | 한 점 안팎으로 흔들림 | 지침 정렬, 강제력, 참조 무결성, 계층 분리 |

판단축은 작성자가 직접 매기지 않는다.
자기 산출물을 자기가 채점하면 후하게 나오기 때문이다.
채점은 작성과 다른 세션이나 에이전트가 한다.

공개 저장소 [fos-skills](https://github.com/jon890/fos-skills)가 2026-07-27 에 이 구조로 채점 도구를 넣었다.
커밋 메시지는 도입 이유를 이렇게 적었다.
기준점 없이 고쳐 와서 개선 여부를 소급 측정할 수 없었다는 것이다.
스크립트는 본문 분량, 끊긴 참조, 표기 위반을 세고, 채점표는 판단축 네 가지를 0점에서 3점으로 매겼다.

### 기준값을 먼저 남기고, 검사기는 첫 실행에서 값을 낸다

구조를 바꾸기 직전에 기준값을 기록해 두면, 변경 뒤 줄 수가 달라졌을 때 지시 내용이 바뀐 것인지 순수한 이동인지 나중에 구분할 수 있다.
기준값이 없으면 개선했는지 되돌릴 수조차 없다.

끊긴 참조 검사는 만들자마자 결함을 하나 찾았다.
두 스킬이 다른 스킬 번들에 있는 파일 경로를 자기 번들의 파일처럼 적고 있었다.
검사기를 만드는 일이 첫 실행에서 가치를 낸 사례다.

### 소비하는 곳이 없으면 쌓지 않는다

이 채점 도구는 같은 저장소에서 2026-09-04 에 제거됐다.
커밋 메시지가 적은 이유는 누적 점수를 소비하는 곳이 없었다는 것이다.
채점 도구는 점수를 보고 무언가를 바꾸는 사용처가 있을 때만 유지할 값이 있다.
이 판단은 [하네스 회고는 새 문서로 쌓지 않고 종류에 맞는 기존 단일 소스에 환원한다](./retrospective-to-single-source.md)와 같은 기준이다.

## 정리

| 질문 | 답 |
| --- | --- |
| 자동 최적화를 붙일 수 있는가 | 채점 신호와 held-out 검증셋이 있는 스킬(A, B 계층)만 붙인다 |
| 채점은 어떻게 나누는가 | 정적 검사를 바닥으로, LLM judge 를 천장으로 둔다 |
| 어느 항목을 정적 검사에 넣는가 | 정당한 용례가 거의 없는 명백한 항목만 넣는다 |
| 정적 검사를 믿으려면 | spot-check 로 오탐을 먼저 제거한다 |
| 스킬 문서 자체를 채점한다면 | 기계축은 스크립트로, 판단축은 작성자가 아닌 쪽이 매긴다 |
