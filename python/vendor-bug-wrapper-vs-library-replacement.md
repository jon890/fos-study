# 외부 패키지 버그 우회: 상속 wrapper 와 라이브러리 교체

pip 으로 설치한 외부 패키지에서 버그를 만나면 패키지 코드를 직접 고칠 수 없다.
설치 디렉터리의 파일은 패키지를 업데이트하면 덮어써지기 때문이다.
선택지는 문제 메서드만 감싸서 우회하는 방법과, 아예 다른 라이브러리로 바꾸는 방법이다.

이 글은 두 선택지의 비용을 비교하고, 어느 쪽이 맞는지 추측 대신 PoC(Proof of Concept, 실증 코드)로 정하는 방법을 정리한다.
Java 개발자에게는 서드파티 jar 의 버그를 만났을 때 서브클래스로 덮어쓸지 의존성을 교체할지 고르는 문제와 같다.

## 두 선택지

### A안, 상속 wrapper 로 최소 수정

문제가 있는 메서드만 하위 클래스에서 재정의해 우회한다.
패키지 본체는 그대로 두므로 변경 범위와 회귀 위험이 가장 작다.
다만 그 패키지가 가진 다른 알려진 한계는 그대로 남는다.

```python
from vendor_pkg import Parser

class PatchedParser(Parser):
    def parse_item(self, raw):
        # 버그가 있는 입력만 먼저 보정한 뒤 원래 구현에 넘긴다
        return super().parse_item(sanitize(raw))
```

위 코드는 구조를 보이기 위한 의사코드이고 `vendor_pkg` 와 `sanitize` 는 가상의 이름이다.

### B안, 라이브러리 교체

한 번에 여러 한계를 해소할 수 있다.
대신 출력 형식이 달라지므로 기존 정상 입력에 대한 회귀 비교가 필수이고, 작업 규모도 커진다.

| 구분 | A안 wrapper | B안 교체 |
| --- | --- | --- |
| 변경 범위 | 문제 메서드 하나 | 사용하는 호출 지점 전체 |
| 회귀 위험 | 작다 | 출력 형식 변화로 큼 |
| 다른 한계 | 그대로 남음 | 함께 해소될 수 있음 |
| 배포 영향 | 의존성 그대로 | 의존성과 전이 의존성 변경 |

## 결정 방식

어느 쪽이 맞는지는 추측하지 않고 PoC 로 정한다.
로컬에 후보 라이브러리를 설치하고, 정상 입력 표본과 실제로 실패한 입력으로 현행 구현과 출력을 비교한다.
이 비교 결과가 A안과 B안 중 하나를 근거로 고르게 해 준다.

교체가 wrapper 와 비슷한 비용으로 추가 한계까지 해소한다면 교체가 낫다.
예를 들어 현행 패키지가 지원하지 않는 입력 형식을 후보가 지원한다면, wrapper 로는 얻을 수 없는 이득이다.

## 교체할 때 점검할 것

- 기존 구현이 하던 후처리를 새 출력에도 적용한다. 제어 문자 제거 같은 정리 단계가 여기 해당한다.
- 출력 형식 변화가 회귀인지 의도된 개선인지 표본 비교로 확인한다.
- 채택 전에 라이선스를 확인한다. AGPL 처럼 서비스에 영향을 줄 수 있는 라이선스를 피할 수 있는지 본다.
- 전이 의존성이 이미 설치되어 있는지 확인한다. 새로 끌려오는 의존성은 배포 이미지와 충돌 가능성을 늘린다.
- 비정상 입력에서 명확한 예외를 내는지 확인한다. 조용히 빈 결과를 돌려주는 라이브러리는 장애를 가린다.

## 정리

- 외부 패키지 파일은 직접 고치지 않는다. 업데이트 시 덮어써진다.
- wrapper 는 변경이 작지만 다른 한계가 남고, 교체는 한계를 한꺼번에 풀지만 회귀 비교가 필수다.
- 선택은 후보를 로컬에 설치해 실제 입력으로 비교한 PoC 결과로 한다.
- 교체한다면 후처리, 출력 변화, 라이선스, 전이 의존성, 예외 동작을 점검한다.
